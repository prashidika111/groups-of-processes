5.x.1 Approach

The Proposed Methodology describes how ActivityOS is intended to be constructed and operated — it is a design specification, not a claim that the system is already implemented. The coding review that follows will demonstrate the actual, working prototype; this section demonstrates the engineering reasoning that the prototype is built from.

The architecture reuses the component chain established in Review 1 (Figure 2): Process Grouper → Activity Manager → Resource Monitor / Activity Control Engine → OS System Calls → Operating System, with the Timeline Logger and Dashboard as reporting surfaces. No new component is introduced here; this section makes that chain concrete by tracing it against specific operations, specific data, and specific Linux mechanisms.

5.x.2 Layered Construction

The architecture is read top-to-bottom as the conceptual flow from user intent through the proposed activity layer to existing operating-system mechanisms. The Process Grouper establishes the activity–process relationship, after which the Activity Manager maintains that mapping for subsequent monitoring and control. The Resource Monitor and Activity Control Engine operate on this maintained membership rather than independently rediscovering it. Every proposed component sits above a fixed boundary: below that boundary, only unmodified Linux mechanisms are used — process listing, POSIX signals (SIGSTOP/SIGCONT), and priority adjustment (setpriority()/nice). Nothing below the boundary is altered by this project; ActivityOS's contribution is entirely the decision and representation layer above it. The full arrangement is shown in Figure 1.

5.x.3 Operation Workflows

Four representative operations are traced individually, each through the same five stages — user input → component → processing → underlying mechanism → result — so that no operation is described as an unsupported black box:

  • Create Activity + Associate Processes — the one workflow with manual input at the membership level. This is a deliberate scope decision (Review 1, §7.1): automatic activity detection is a separate research problem, out of scope for this prototype. The Process Grouper validates user-selected PIDs against the OS process table and the Activity Manager creates the Activity record.
  • Monitor Activity Resources — the Resource Monitor samples process CPU accounting information from /proc/<pid>/stat over an observation interval and computes per-process CPU utilisation from it; memory usage is obtained directly from /proc/<pid>/status. Both are aggregated across the activity's member processes and exposed as one CPU/memory value on the Dashboard.
  • Pause / Resume Activity — the strongest representative operation, and the one selected for the full end-to-end trace below (§5.x.4, Figure 2).
  • Change Activity Priority — structurally identical to pause/resume: membership is resolved, the operation is translated per-process, setpriority() is called once per member PID. This translation — one activity-level command fanning out into per-process OS operations — is the central implementation mechanism through which the proposed activity abstraction is connected to existing process-level controls; it is not presented as a novel scheduling technique.

5.x.4 End-to-End Trace — "Pause Study"

This is the single trace chosen to demonstrate that the architecture is coherent from human intent to kernel-level effect, with no unexplained step (Figure 2):

  1. Human intent — user clicks Pause on the "Study" activity.
  2. Activity layer — Activity Manager looks up the Activity record by activity_id.
  3. Membership resolution — the stored member_processes[] mapping is the source of membership for this operation; the Control Engine may validate that each stored PID is still available before issuing the corresponding OS operation, since member processes can exit between grouping and control operations.
  4. Control component — the resolved PID set is handed to the Activity Control Engine.
  5. Translation — the single activity-level "pause" request is translated into one process-level operation per member PID.
  6. Linux mechanism — the Control Engine attempts kill(pid, SIGSTOP) for each member PID and records the outcome per process; failures (permission denied, PID no longer present) are recorded rather than silently treated as success.
  7. Kernel effect — for each process the signal reaches, the kernel scheduler stops scheduling it, using standard, unmodified signal handling. The kernel itself has no concept of "Study" — it only ever sees ordinary SIGSTOP signals.
  8. Side effect — the Timeline Logger records {activity: "Study", action: "pause", timestamp} into the activity's event_log[]. This is logged because the Control Engine made a decision, not because the kernel reported anything — the kernel is never queried for activity information.
  9. Result — the activity is marked paused according to the prototype's defined success policy (e.g. all-members-succeeded, or best-effort with failures recorded); the Dashboard reflects this application-level state. Resume follows the identical path with SIGCONT.

5.x.5 Data Model

Each Activity is a record the Activity Manager owns — a data structure internal to this layer, not a kernel object (Figure 3):

FieldPopulated by
activity_idsystem-generated at creation; unique lookup key
nameuser-supplied, human-visible label (not guaranteed unique)
member_processes[]Process Grouper, at creation
stateapplication-level activity state; Activity Control Engine sets it according to the prototype's defined success policy
priority_levelrequested/activity-level priority setting; Activity Control Engine, with per-process application results tracked separately where necessary
resource_snapshotResource Monitor, recomputed on each poll
event_log[]maintained by the Timeline Logger, as the activity's application-level history

Activity-level resource figures are never independently measured — memory is read directly from /proc/<pid>/status; CPU utilisation is derived by the Resource Monitor from /proc/<pid>/stat accounting data sampled over an interval. Both are aggregated across member_processes[].

activity_id is used for lookup rather than name, since two activities could otherwise share a user-chosen name.

priority_level and resource_snapshot are the system's representation of applied/observed state, not a guarantee of authoritative kernel reality — per-process operations can fail (e.g. permission denied) or a process can exit between polls, and such outcomes are recorded rather than assumed.

5.x.7 Assumptions and Simplifications

  • Activity membership is assigned manually by the user at creation time; the prototype does not attempt automatic activity detection.
  • The prototype targets a single OS (Linux) and a single set of primitives (process listing, /proc, POSIX signals, setpriority()), consistent with the scope defined in Review 1 §1.3 and §7.5.
  • The Timeline Logger records only actions initiated by the Activity Control Engine; it does not observe the kernel, and the kernel is never queried for activity-related information.
  • cgroups are acknowledged as a complementary, lower-level enforcement mechanism but are not used in this prototype.
  • A member process may exit between when it was grouped into an activity and when a later monitoring or control operation is attempted on it.
  • Control operations may fail for individual member processes (e.g. insufficient permissions, PID no longer present); such outcomes are recorded rather than assumed to have succeeded.
  • Activity-level state (state, priority_level, resource_snapshot) represents the application layer's own record of intended and observed status, not an OS- or kernel-level notion of "activity" — the kernel has no such concept.
